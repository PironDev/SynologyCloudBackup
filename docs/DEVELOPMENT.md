# Разработка CloudBackup

## Состав репозитория

Этот публичный репозиторий содержит упаковку, CI, выпуск релизов и документацию. Исходный код приложения расположен в приватном Git-сабмодуле `app/`.

CI публичного репозитория получает доступ к сабмодулю через секрет `SUBMODULE_TOKEN`. В публичных журналах CI выводятся только итоги проверок.

## Работа с сабмодулем

1. Получите доступ к приватному репозиторию исходников.
2. Клонируйте публичный репозиторий вместе с сабмодулями:

   ```sh
   git clone --recurse-submodules git@github.com:PironDev/SynologyCloudBackup.git
   ```

3. Перейдите в каталог `app/`.
4. Создайте ветку и внесите изменения в исходный код.
5. Отправьте изменения в приватный репозиторий.
6. В публичном репозитории обновите указатель сабмодуля на проверенный коммит.

Не копируйте содержимое приватного сабмодуля в публичный репозиторий.

## Локальная сборка

Требуется версия Go из `app/go.mod`.

Из каталога `app/` выполните:

```sh
packaging/build.sh 1.0.0
go test -race ./...
```

Сборка создаёт SPK в каталоге `dist/`. Запасной режим отдельной вкладки включается командой:

```sh
UI_MODE=tab packaging/build.sh 1.0.0
```

Пакет собирается для x86_64, arm64 и armv7.

## CI

Workflow CI проверяет формат Go, `go vet`, тесты с `-race`, shell-скрипты, JavaScript и сборку SPK. Для доступа к исходникам нужен fine-grained token `SUBMODULE_TOKEN` с правом чтения только приватного репозитория исходников.

Публичный CI выводит сокращённый результат проверок. Подробный вывод следует смотреть в workflow приватного репозитория.

## Выпуск релиза

Релизы публикуются в публичном репозитории. Пакет также проверяет обновления в этом репозитории.

1. Отправьте проверенный коммит исходников в приватный репозиторий.
2. Обновите указатель сабмодуля в публичном репозитории.

   ```sh
   git submodule update --remote app
   ```

3. Зафиксируйте новый указатель сабмодуля.
4. Создайте тег `vX.Y.Z` и отправьте его.

   ```sh
   git tag v1.2.3
   git push --follow-tags
   ```

Workflow `release` собирает SPK из коммита сабмодуля, указанного в теге. Workflow подписывает обновление и публикует релиз.

Для выпуска нужны:

- секрет `SUBMODULE_TOKEN`;
- секрет `UPDATE_SIGN_KEY`;
- переменная `UPDATE_PUBKEY`;
- окружение GitHub Actions `production`.

В репозитории исходников нет workflow публикации релизов.

## Параметры службы

Файл `/var/packages/<Пакет>/var/service.conf` задаёт разрешённых пользователей DSM и сетевые параметры службы. После изменения перезапустите пакет.

- `ALLOW_USERS="vasya,petya"` разрешает доступ указанным пользователям.
- `ALLOW_USERS="*"` разрешает доступ всем пользователям DSM.
- `GATEWAY_ADDR` задаёт адрес WebDAV-шлюза.
- `PROXY_ADDR` задаёт локальный адрес CGI-моста.
- `WEB_ADDR` задаёт необязательный адрес отдельного интерфейса.

Пользователь пакета не получает права пользователя DSM, который вошёл в веб-интерфейс. Выдавайте ему только те права файловой системы, которые нужны для расписаний и фоновых передач.

## Границы проверки

CI не проверяет работу на физической NAS. Для релиза отдельно проверьте установку на поддерживаемой версии DSM, вход пользователя, права на личные папки и передачу файлов через File Station.

Реальные сервисы облаков и ограничения аккаунтов могут отличаться от имитаций в тестах. Проверьте основные операции на тестовом аккаунте перед рабочим запуском.
