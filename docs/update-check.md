# Проверка обновлений

Статус: план, код не написан.

## 1. Цель

Приложение сообщает, что на GitHub вышла новая версия пакета. Установку выполняет пользователь.

## 2. Допущения

1. Репозиторий публичный. Токен в приложение не вшивается.
2. Каждый релиз содержит пакет `CloudBackup-<версия>.spk`.
3. Каждый релиз содержит файлы `SHA256SUMS` и `SHA256SUMS.sig`.
4. Ключ подписи хранится вне репозитория.
5. Данные приложения сохраняются при обновлении пакета через Центр пакетов. Это нужно проверить на NAS.

## 3. Требования

1. R1. Приложение запрашивает `GET https://api.github.com/repos/<владелец>/<репозиторий>/releases/latest`.
2. R2. Приложение сравнивает версии по правилам semver.
3. R3. Версия сборки задаётся при сборке через `-ldflags -X nascloud/internal/version.Version=<версия>`.
4. R4. Приложение выбирает ассет по имени своего пакета.
5. R5. Перед показом баннера приложение проверяет подпись `SHA256SUMS` публичным ключом.
6. R6. Перед установкой приложение проверяет SHA-256 пакета по `SHA256SUMS`.
7. R7. Результат проверки кешируется в `store` на 24 часа.
8. R8. Проверку можно выключить в настройках.
9. R9. Установку выполняет пользователь через Центр пакетов. Приложение не запускает `synopkg`.
10. R10. Ошибки проверки пишутся в журнал. Интерфейс их не показывает, кроме строки в настройках.

## 4. Шаги реализации

1. Добавить в `internal/version` переменную `Version`. Она уже есть. Проверить, что `build.sh` передаёт версию через `-ldflags`.
2. Добавить пакет `internal/updater`:
   1. функция `Latest(ctx, repo, asset)` запрашивает релиз и возвращает версию, ссылку на пакет и ссылки на `SHA256SUMS` и `.sig`;
   2. функция `Verify(sums, sig, pubkey)` проверяет подпись через `crypto/ed25519`;
   3. функция `Check(ctx, ...)` сравнивает версии и возвращает результат.
3. Добавить в `store` поле с результатом последней проверки и временем проверки.
4. Добавить в `internal/web` маршрут `GET /api/update` и запуск проверки раз в 24 часа.
5. Добавить в интерфейс баннер «Доступна версия X» и ссылку на страницу релиза.
6. Добавить переключатель «Проверять обновления» в настройки.
7. Добавить в `packaging/build.sh` публичный ключ и имя репозитория.
8. Написать тесты (раздел 5).

## 5. Тесты

1. T1. Сравнение версий: `1.0.1 > 1.0.0`, `1.10.0 > 1.9.0`, `1.0.0-beta < 1.0.0`.
2. T2. Разбор ответа GitHub. Тест на `httptest`, без реального GitHub.
3. T3. Подпись верна: проверка проходит.
4. T4. Подпись неверна: проверка не проходит, баннер не показывается.
5. T5. SHA-256 пакета не совпадает: установка помечена как небезопасная.
6. T6. Ответ 404 от `/releases/latest` (нет опубликованных релизов) обрабатывается как «обновлений нет», без ошибки в журнале.
7. T7. Ассета своего пакета нет: проверка возвращает понятную ошибку.
8. T8. GitHub недоступен: результат кеша не меняется, ошибка пишется в журнал.
9. T9. Проверка выключена: запрос к GitHub не отправляется.

## 6. Сбои и граничные случаи

1. F1. Нет интернета на NAS. Проверка пишет предупреждение и повторяется в следующий интервал.
2. F2. GitHub вернул 403 из-за лимита запросов. Проверка ждёт следующего интервала. Лимит без токена: 60 запросов в час с одного IP.
3. F3. Релиз без файла `SHA256SUMS.sig`. Баннер не показывается.
4. F4. Ключ подписи потерян. Старые установки не получат обновление. Новый ключ требует выпуска новой версии приложения со старым ключом в списке доверенных.
5. F5. Пользователь установил старую версию поверх новой вручную. Приложение сравнивает версии и не предлагает понижение.

## 7. Приватность

Запрос к GitHub раскрывает IP адрес NAS и версию приложения. Настройки должны показывать это явно.

## 8. Критерии готовности

1. Все тесты из раздела 5 проходят. Команда: `go test ./internal/updater/ ./internal/web/`.
2. `packaging/build.sh` создаёт `SHA256SUMS` и подписанный файл. Подпись проверяется скриптом до загрузки пакета в релиз.
3. На NAS баннер появляется после выхода тестового релиза с более высокой версией.
4. Установка через Центр пакетов сохраняет настройки и задания.
